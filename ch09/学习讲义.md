# 第 9 章 · WebBot 训练：显存、并行与实验管理

**本章产物**是将前三份工程成果放进大规模训练循环的能力。先看 [01_pretrain.py](01_pretrain.py) 的 batch 读取、异常梯度限制、优化器、验证和保存，再看 [02_generate.py](02_generate.py) 怎样使用权重与分词器。

## 9.1 梯度累积

显存不足以一次装入大 batch 时，拆成几个 micro-batch。每个小批求梯度，累加后只调用一次 `optimizer.step()`。具体实现中，每个等大小 micro-batch 的平均 loss 除以累积次数。若按不同数量的有效 token 给 loss，须用有效 token 总数正确加权。有效 batch 为“每卡 micro-batch × 累积次数 × 数据并行进程数”。脚本的 32 × 4 表示每进程 128 个序列，每个序列最多 1024 个训练位置。日志里 `effective_batch_size` 未乘进程数。

## 9.2 梯度检查点

反向传播通常需要前向中间结果。检查点只留部分激活，反传需要其余内容时重做前向，换取更小的激活峰值。它与保存可恢复训练的 checkpoint 文件是两个概念。前者增加计算，后者应包括恢复所需的优化器、步数、随机数和数据状态。当前 WebBot 入口演示模型保存，恢复完整优化器训练状态需扩展。梯度检查点是本章概念，入口未启用。

## 9.3 分布式数据并行

DDP 在每个进程复制模型和优化器，每个进程读不同数据并求局部梯度，然后通过 all-reduce 同步梯度，再各自更新。当前脚本通过 `RANK`、`LOCAL_RANK` 和 CUDA/NCCL 初始化。要在累积时省通信，PyTorch 的 `no_sync()` 要包住对应的前向和反向；源码只包反向，不能把它当作已验证的免同步配置。真实多机还应验证全局 rank 0、采样覆盖、同步和异常退出。稳妥的做法是先单进程验证数值，再小规模验证并行精度和吞吐。[PyTorch DDP 说明](https://docs.pytorch.org/docs/stable/generated/torch.nn.parallel.DistributedDataParallel.html)。

## 9.4 ZeRO

DDP 会在多卡上重复存同样的参数、梯度和优化器状态。ZeRO 分阶段切分优化器状态、梯度、参数，让每张卡只常驻一部分，再在需要时通信。切分越彻底，内存节约越多，也越依赖通信路径与重新聚合调度。当前训练入口是 DDP，ZeRO 是书中扩展。[ZeRO 原论文](https://arxiv.org/abs/1910.02054)。

## 9.5 Muon

Muon 对某些二维权重的动量更新做近似正交化，常用 Newton–Schulz 迭代，以调整不同矩阵方向的更新尺度。把它理解成对“整块矩阵的更新方向”做处理；AdamW 主要使用逐元素矩。实际配置常保留 AdamW 处理嵌入、偏置等不适用的参数。当前脚本使用 AdamW，可以先认识它，再阅读 [Muon 作者实现](https://github.com/KellerJordan/Muon)。

## 9.6 实验记录与 9.7 训练和生成

W&B 负责记录超参、训练损失、验证损失和学习率。想本地看曲线，可设 `WANDB_MODE=offline` 后运行，或用 `WANDB_MODE=disabled` 跳过记录。定位指标时注意源码训练 loss 日志反映最后一个 micro-batch，若想记录整次更新的均值须累加统计量。对比模型要锁定词表、验证文件和预算。

默认需 `webbot/owt_train.bin`、`owt_valid.bin` 和对应词表。可对照 [运行指南](../运行指南.md) 追踪依赖。长训前先校验输入 dtype、最小训练步、成功保存和重新加载。扩展到真实数据时要单独评估训练文本覆盖、网页重复、评测泄漏、可复现配置及下游任务质量。最后的网页续写是检查模型能力的一项观察。

## 可运行实验 · 微批梯度与大批一致

```python
import torch

w = torch.nn.Parameter(torch.tensor(0.4))
x = torch.tensor([1.0, 2.0, 3.0, 4.0])
y = 2 * x
((w * x - y) ** 2).mean().backward()
reference = w.grad.clone()

w.grad = None
for a, b in zip(x.chunk(2), y.chunk(2)):
    loss = ((w * a - b) ** 2).mean() / 2
    loss.backward()
torch.testing.assert_close(w.grad, reference)
print(w.grad.item())
```

预期约 `-24`。把 `/2` 去掉再观察梯度，这能解释为什么累积要记录归约方式。


## 实际跑一次 WebBot 小模型更新

以下调用 WebBot 的官方 GPT 类，在 CPU 上跑两个微批，完成一次更新。它验证模型、GQA、目标对齐、反传和累积能接起来。训练数据是人工生成的小整数，损失只用于检查计算路径。

```python
import torch
import torch.nn.functional as F
from webbot.model import GPT

torch.manual_seed(7)
torch.set_num_threads(1)
model = GPT(32, 16, 32, 4, 2, 1, 64, 10000)
optimizer = torch.optim.AdamW(model.parameters(), lr=0.001)
optimizer.zero_grad()

for _ in range(2):
    ids = torch.randint(0, 32, (2, 9))
    x, y = ids[:, :-1], ids[:, 1:]
    logits = model(x)
    loss = F.cross_entropy(logits.flatten(0, 1), y.flatten())
    (loss / 2).backward()
grad_norm = torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)
assert torch.isfinite(grad_norm) and grad_norm > 0
optimizer.step()
print(tuple(logits.shape), round(loss.item(), 4), round(grad_norm.item(), 4))
```

预期形状为 `(2,8,32)`，梯度范数为正且有限。下一步读原版入口时，逐一找到多出来的组件：memmap、调度日程、混合精度、编译、分布式、验证、日志和保存。每加一项，先判断它改变的是模型数学、训练数据、执行性能还是观测方式。


## 训练前先算批量，出问题再按内存来源排查

假设 2 张卡、每张卡一次读 32 条、每 4 次反传更新一次。每次更新看见 `2×32×4=256` 条序列，长度 1024 时最多监督 262,144 个位置。若报告中只写“batch 32”，读者不知道这是微批还是全局批量。梯度累积会降低每次前向的激活峰值，优化器状态和模型权重依然要存。在使用 DDP 时，各进程普通情况下仍保存一份权重。ZeRO 分片才会改变这部分重复开销。[ZeRO 论文](https://arxiv.org/abs/1910.02054)

| 何时内存吃紧 | 可以先检查什么 |
|---|---|
| 模型刚创建就不够 | 参数量、权重 dtype、是否每张卡都复制 |
| 前向能跑，小批量反传就不够 | 激活、序列长度、微批、activation checkpoint |
| 第一次 AdamW 更新时增长 | 优化器状态的首次分配 |
| 生成越久越容易超出 | KV 缓存、请求数、有效序列长度 |

遇到显存问题先定位发生阶段，再选择手段。activation checkpoint 重算前向中的部分激活。另一种训练 checkpoint 写文件，以便进程中途停止后继续训练。恢复时先核对模型、优化器、当前步、学习率日程和数据采样状态，再看是否要求恢复随机状态。[PyTorch activation checkpoint 文档](https://docs.pytorch.org/docs/stable/checkpoint.html)

**自检与答案**：两张卡各产生一个平均梯度，为什么简单平均可能跟单卡不一致？若两个进程有不同数量的有效 token，各自产生的平均值必须按各自计数加权。在默认的等样本数示例里，平均才和全局均值一致。
