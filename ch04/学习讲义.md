# 第 4 章 · 分词器提速：从 CodeBot 到 StoryBot

**本章产物**是能在大文件上训练和编码的 BPE。StoryBot 使用 TinyStories，短篇故事更适合检查人物、事件顺序和结尾。算法的共同目标是保留第 1 章的 token 语义，并降低时间与峰值内存。训练合并表和用合并表编码是两个独立的性能问题。

## 4.1 去重：相等片段算一次，频次还是都要算

如果预分词得到某个单词 10,000 次，可以存一个字节序列和权重 10,000。统计相邻对时，每次贡献应乘上权重。这样能保持全语料的统计意义，也减轻内存和重复扫描。遇到频次平局，顺序改变可能改变并列赢家，比较结果前应先明确 tie-break。看 [01_bpe_optimize.py](01_bpe_optimize.py)。

## 4.2 部分更新：只重算受合并影响的数据

一次合并只影响含目标相邻对的片段。维护“相邻对 → 涉及片段”的索引。合并之前从全局计数减掉旧贡献，合并之后加回新贡献，并更新索引，流程类似维护数据库索引。缓存占用一些内存，却省掉查遍全部片段的时间。最容易犯错的是计数乘权重，以及清理相邻关系。看 [02_bpe_cache.py](02_bpe_cache.py)。

## 4.3～4.4 分片与并行：限制每次读入的数据

用字节偏移定位文件，尽量沿文档结束符切分，让每块可以独立解码。随机截断可能把 UTF-8 字符、特殊 token 或正则片段切开，导致结果变化。查看 [03_bpe_chunk.py](03_bpe_chunk.py) 与 [find_chunk_boundaries](../storybot/tokenizer.py)。每个进程预分词并计算自己的词频，主进程合并统计。文件 I/O、进程启动、进程间传输都会影响收益。Python 的 spawn 环境中，从脚本的 `if __name__ == "__main__":` 入口运行，避免子进程重复启动子进程。看 [04_bpe_parallel.py](04_bpe_parallel.py)。

## 4.5 评估：把优化目标分开量

同一语料分别测训练时长、峰值内存、编码字节每秒、压缩比和 round-trip。词表变大常能压缩某些文本，模型的输入与输出词表层也会变大。StoryBot 与 CodeBot 的训练语料和词表大小同时变化；如果想比较算法速度，须锁定数据、词表预算和合并规则。拿保留语料检验英文故事、代码和中文的表现。

## 4.6～4.7 加速编码与写盘

编码每个片段，按已学合并顺序挑可用的相邻对。尽早停止在没有规则时的扫描，避免对无关组合做冗余工作。可进一步用邻接索引或堆实现增量处理，但应先以官方实现为基准验证 ID 序列。读 [06_encode_optimize.py](06_encode_optimize.py)。

大批数据可并行编码为临时块，保留块编号与 token 数量，最后按原顺序拼接。用相同 dtype 的 `np.memmap` 写磁盘映射区间，可避免把全部 token 存在 Python 列表里。数据还是会消耗磁盘和系统页缓存。看 [07_encode_parallel.py](07_encode_parallel.py) 和 [StoryBot 分词器](../storybot/tokenizer.py)。源文件开始/结束标记不足时分片数可能少于请求值。

## 可运行实验 · 去重前后计数相同

```python
from collections import Counter, defaultdict
from storybot.tokenizer import count_pairs

chunks = [b"aba", b"aba", b"ab"]
regular, weighted = defaultdict(int), defaultdict(int)
for chunk in chunks:
    count_pairs(list(chunk), counts=regular)
for chunk, count in Counter(chunks).items():
    count_pairs(list(chunk), weight=count, counts=weighted)
assert regular == weighted
print(dict(weighted))
```

从根目录运行，`ab` 的计数应是 3，`ba` 是 2。接着让一个 pair 在同一片段中重复，检查你的解释仍成立。完整训练方式参见 [运行指南](../运行指南.md)。


## 实际跑一次多进程

在仓库根目录运行 `.venv/bin/python 小实验/storybot_bpe.py`。脚本使用官方共享实现，把几篇短文写进临时文件，用 2 个进程训练 265 词表的模型，分块编码，再用 NumPy 读回 `uint16`。校验整段编码和分片编码逐 ID 相同，最后把 ID 解码回原文。[StoryBot 小实验](../小实验/storybot_bpe.py)。

下一步，把进程数改 1，或减少语料中的结束标记，观察分片数和相等性校验。这个规模上多进程启动耗时可能大于可节省的运算。


## 先复现语料，再验证优化

TinyStories 原论文选择篇幅短、语言较简单的故事，是为了检查小模型在受控文本分布中能否写连贯英文。本书作者的数据包采用 TinyStories V2，并提供单独的训练和验证切分。用它对照真实故事数据时，压缩比、训练耗时和生成质量应分别观察。[TinyStories 原论文](https://arxiv.org/abs/2305.07759) · [作者数据卡](https://huggingface.co/datasets/koki0702/zero-llm-data)

假设预分词得到三条 `aba` 和一条 `abb`。合并 `ab → X` 前，旧片段贡献 `ab:4, ba:3, bb:1`。合并后得到三条 `Xa` 和一条 `Xb`，新贡献为 `Xa:3, Xb:1`。这就是缓存更新要执行的“先减旧贡献，再加新贡献”。如果把三条重复数据只按一条计算，虽然分片编码还可能正常，后续合并表已经变了。

跑过本章文件实验后，试着只改变一件事，例如进程数。验证顺序可以固定为：同样文本能还原 → token 序列逐项相等 → 输出文件字节长度等于 token 数乘 2 → 最后比较用时。若发现组装结果颠倒，优先检查是否按分片原始顺序写回，不能按进程完成顺序直接拼接。对应 [StoryBot 编码器](../storybot/tokenizer.py)。

**自检与答案**：为什么分片编码要事先确定文档边界？为了使每块内的 UTF-8 和预分词状态与整段处理一致。某些切法能无损还原原文，却因合并边界不同产生不同 ID。
