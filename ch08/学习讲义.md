# 第 8 章 · WebBot 模型：让更长、更大的 Transformer 跑得动

本章的官方代码集中在 [webbot/model.py](../webbot/model.py)。先确认你能解释第 5 章的 RoPE、K/V 缓存及 prefill/decode，再比较本章改变了哪些成本。

## 8.1 选模型尺寸

词表、层数、宽度、上下文长度与训练 token 预算要一起选。可训练参数越多，权重、梯度和 Adam 状态越贵。长上下文主要增加序列计算、激活和 KV cache，需要另行预算。WebBot 的默认超参在 [第 9 章入口](../ch09/01_pretrain.py)，例如上下文 1024、宽度 768、12 层、12 个查询头、4 个 KV 头。用 `sum(p.numel() for p in model.parameters())` 得参数量。训练中还要为激活保留显存。

## 8.2 FlashAttention 改善内存访问

普通写法把注意力得分矩阵写入显存，softmax 后再读回来处理。FlashAttention 分块处理并维护 softmax 的归一化与稳定量，避免把巨大中间矩阵完整来回搬运。精确注意力在数值误差范围内保持原语义，稠密注意力的计算规模仍随序列长度近似平方增长。官方调用 PyTorch `scaled_dot_product_attention`，不同 dtype、硬件、mask 和张量形状可能选择不同后端。[FlashAttention](https://arxiv.org/abs/2205.14135) · [PyTorch SDPA](https://docs.pytorch.org/docs/stable/generated/torch.nn.functional.scaled_dot_product_attention.html)。

## 8.3 GQA 减少 K/V 头与缓存

MHA 中每个查询头有自己的 K/V。GQA 让多组查询头分别共享 K/V。WebBot 的 12 个 Q 头分配给 4 组，每 3 个 Q 头用一组 K/V，仍拥有各自的查询投影。MQA 把共享推进到只用一个 KV 头。固定批量、上下文、头维和层数时，GQA 相比 12 个 KV 头理论上的 KV 缓存元素数约为三分之一。实际计算和带宽收益依赖后端。注意构造时 Q 头数一般要能被 KV 头数整除。读 `MultiHeadAttention.forward` 的 `enable_gqa=True`。[GQA 原论文](https://arxiv.org/abs/2305.13245)。

## 8.4 MoE 把 FFN 改为若干专家

路由器给每个 token 的专家打分，选少数专家处理，然后加权合并。总参数可以很大，每个 token 只激活其中一部分。代价包括权重存储、路由不均衡、跨设备通信和复杂的调度。当前 WebBot 的 `Block` 使用稠密 SwiGLU。作为 2026 年的现代对照，可以看 DeepSeek-V4-Flash 的官方模型卡如何描述模型结构，再把“总参数”“活跃参数”“上下文成本”分别对应本章。[官方模型卡](https://huggingface.co/deepseek-ai/DeepSeek-V4-Flash)。

## 8.5 编译与 8.6 上下文扩展

`torch.compile` 捕获并优化 PyTorch 运算图，可能融合算子，降低调度成本。首次运行包含编译时间，形状变化可能重新编译。先验证 eager 与 compile 输出，再用预热和多次计时比较。当前 [训练入口](../ch09/01_pretrain.py) 调用 compile，CPU 小实验采用 eager。

上下文长度上限要考虑位置编码范围、数据和模型是否在相应长度上训练过，以及显存。RoPE 的缩放或插值调整角度范围，可以结合长序列训练及外推评估。能塞进长文本和能用好长文本是两种能力。测试长上下文可把关键事实插到不同位置，检查检索成功率和速度。

## 可运行实验 · 测 GQA 的共享语义

```python
import torch
import torch.nn.functional as F

torch.manual_seed(7)
q = torch.randn(1, 4, 3, 8)
k = torch.randn(1, 2, 3, 8)
v = torch.randn(1, 2, 3, 8)
gqa = F.scaled_dot_product_attention(q, k, v, enable_gqa=True, is_causal=True)
expanded = F.scaled_dot_product_attention(
    q, k.repeat_interleave(2, dim=1), v.repeat_interleave(2, dim=1), is_causal=True,
)
torch.testing.assert_close(gqa, expanded)
print(gqa.shape, k.numel(), k.repeat_interleave(2, dim=1).numel())
```

预期 `[1,4,3,8]`，K 从 48 个元素显式展开则为 96。此实验验证共享的计算含义，性能需要目标设备实测。

## 怎样选择模型优化：动手算一张成本表

沿用 WebBot 的 12 层、1024 上下文、头维 64，假设每份 K/V 都用 BF16。单条请求的缓存体积可以用 `2 × 层数 × 长度 × KV 头数 × 头维 × 每元素字节数` 估算。如果有 12 个 KV 头则为 36 MiB，使用 4 个 KV 头则为 12 MiB。这里单独计算缓存，不包含权重或内存分配开销。长度翻倍则这笔缓存开销翻倍。稠密注意力在 prefill 的得分矩阵从 `1024×1024` 变到 `2048×2048`，每头的分数数量翻四倍。这个对照能说明同一个长度参数影响多种不同成本。[GQA 论文](https://arxiv.org/abs/2305.13245)

| 遇到的瓶颈 | 优先理解哪种技术 | 先量什么 |
|---|---|---|
| 注意力中间张量搬运很重 | FlashAttention、SDPA 后端 | 相同输入下时间与峰值内存 |
| 多条请求的历史 K/V 占太多内存 | GQA、分页缓存 | 每条缓存体积、并发数量 |
| 想增大模型容量 | MoE | 总参数、每 token 参与计算的参数、路由负载 |
| 同样形状反复运行，算子调度很重 | 编译 | 分开计首次编译与稳态耗时 |
| 输入能装下，但模型忘了开头事实 | 长上下文训练与评估 | 不同位置的事实提取成功率 |

**自检与答案**：为什么调用 SDPA 就能在本机验证注意力正确，但还不能据此宣称跑了 FlashAttention？函数是接口，后端会根据设备、类型和形状选择。验证数学等价和验证硬件内核是两项不同的测量。[PyTorch SDPA 文档](https://docs.pytorch.org/docs/stable/generated/torch.nn.functional.scaled_dot_product_attention.html)
