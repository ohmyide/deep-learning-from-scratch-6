# 第 7 章 · WebBot 的分词器：先测瓶颈，再换实现

## 7.1～7.2 更大的词表与更大的语料

WebBot 用 OpenWebText 类网页文本，代码默认词表 50,000。第 4 章在内存里聚合重复片段能节约大量工作，但网页语料更大、种类更多，预分词统计表本身可能变成瓶颈。打开 [01_bpe_train.py](01_bpe_train.py) 与 [02_bpe_encode.py](02_bpe_encode.py)，它们调用 StoryBot 的实现，修改语料、词表和分片设置。模型必须用同一套合并规则与特殊 token ID。

先运行小样本，分别测**清洗/读取、正则切分、相邻对计数与更新、应用合并、落盘**。计时使用 `perf_counter`，热点排查可用 `python -m cProfile -s cumulative 脚本`。记录原始字节数、耗时、峰值内存、进程数和输出 token 数，必要时另测缓存热启动。对比“单进程”“多进程”的正确性和吞吐，防止只看到进程数上升。

## 7.3 Rust/C++：减少解释器开销

在热点是 Python 对象、循环或线程受限时，可用原生扩展处理核心循环，减少对象分配和跨语言调用。I/O 受限时换语言未必有收益。当前仓库 WebBot 脚本仍复用 Python 分词器。更换实现先固定 Unicode 正则、BPE 合并优先级、特殊符策略和输入规范，再逐条比对 token ID。仅做 round-trip 会漏掉两套规则切法不同的问题。

## 7.4 控制 token 是一项接口设计

文档边界、对话角色、工具消息都可以使用独立标记。每种标记要有稳定的 ID，并决定普通用户文本中的同名字样如何处理。若把角色控制符当成普通输入放行，用户正文可能被错误解释为结构。词表扩展后，嵌入和输出矩阵也要扩展，新增行要经过训练。书中展示扩展思路，当前分词路径主要实现结束标记。

## 7.5～7.6 其他分词策略与字节模型

BPE 偏向合并频繁相邻对。Unigram 从候选词片出发，拟合能解释文本的片段概率并删减候选。WordPiece 也用子词，学习与选择规则有自己的设计。SentencePiece 是可实现多种算法的模型工具。比较时应任选若干测试语料，测长度、切分稳定性、对代码缩进或多语文字的影响。[SentencePiece 原论文](https://arxiv.org/abs/1808.06226)。

字节或 patch 模型可以缩小固定词表带来的负担，却要应对更长的序列。动态把多个字节组为较大的计算单位可缓解该问题。对照 [Byte Latent Transformer](https://arxiv.org/abs/2412.09871)。大词表与短序列、小词表与长序列之间没有通用赢家。

## 可运行实验 · 小语料测吞吐也测正确性

```python
from time import perf_counter
from storybot.tokenizer import BPETokenizer

text = "Once there was a cat. 猫🐈<|endoftext|>\n" * 1000
tokenizer = BPETokenizer({})
start = perf_counter()
ids = tokenizer.encode(text)
seconds = perf_counter() - start
assert tokenizer.decode(ids) == text
print(len(ids), round(len(text.encode()) / seconds), "bytes/s")
```

这里使用零合并的字节词表，方便独立验证。把它换成 [运行指南](../运行指南.md) 推荐的作者产物后再比较 token 数。第 8、9 章拿到的是固定 ID 合约及更大规模的数据。


## 加练 · 用同一词表做性能对照

运行第 4 章的文件编码实验作为正确性基线。选同一块语料，记录读取大小、词表大小与哈希、工作进程数、每个阶段耗时，分别用 1、2、4 个进程跑。把特殊 token 放到很靠近切分边界的位置，检查是否仍完整保留。若替换为 Rust 实现，先比较编码出的整数序列，随后再比较吞吐。这能避免把改变分词行为造成的 token 减少误认为 CPU 加速。

### 如何自己做一次有意义的性能测量

先用同一份文件和规则跑两次。第一次只计预分词，将每个片段计数；第二次分别量实际编码和写文件。每轮记录原始字节数、耗时、输出 token 数和工作进程数。相同文件下，第一次可能包含冷启动和文件缓存。想回答“多进程是否有用”，需要多轮对照中位数。想回答“替换实现是否有用”，还要验证同样的 token 序列。将文本清洗、分词、文件写入混成一个计时，往往无法看出真正的阻塞位置。

**自检与答案**：为何加一个对话角色标记可能需要改模型？新 token 有新 ID，原有输入嵌入和输出词表投影可能没有那一行，模型还需要学习它在输入和输出中的作用。可对照常见对话库如何把角色落实到模型的序列中。[Hugging Face 对话模板说明](https://huggingface.co/docs/transformers/main/chat_templating)
